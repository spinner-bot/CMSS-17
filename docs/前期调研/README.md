# CMSS-17 前期调研 · 总纲

> 本文件是前期调研的**逻辑主干**与**进度看板**。所有中间产物保留在本目录下，不删除。

## 0. 调研要解决的核心问题

团队尚未确认选题方向。本调研**不是**为已定选题做背书，而是**用客观事实把选题"推导"出来**。

因此本调研必须回答的一条主问题是：

> 在「正大杯」的规则约束下，什么样的选题，既能命中真实市场需求、又落在这个团队**真实可执行的能力边界**之内？

## 1. 逻辑链条

调研沿以下链条逐级收敛。**每一级的结论都必须有据可查（标注信息源与证据强度），且上一级的结论是下一级的前提**。

| 层 | 名称 | 要回答的问题 | 产出 | 执行 |
|---|---|---|---|---|
| **L0** | 约束识别 | 赛事要什么？团队能做什么？资源边界在哪？ | 可行解空间 | Codex 采集 + Claude 归纳 |
| **L1** | 机会识别 | 可行空间内，哪些真实需求尚未被满足？ | 候选痛点池 | Codex 采集 |
| **L2** | 数据可行性 | 这些机会能否被**合法可得的数据**支撑？ | 数据可得性判定 | Codex 采集 |
| **L3** | 技术可行性 | AI 能带来什么**不可替代**的增量？ | 技术方案与边界 | Codex 采集 |
| **L4** | 竞品扫描 | 已有方案做到哪一步？我们差在哪、强在哪？ | 差异化论证 | Codex 采集 |
| **L5** | 方向收敛 | 综合上述，哪几个方向可行？各自代价与前景如何？ | **方向簇建议书**（多个相近方向 + 对比 + 主推） | **Claude 独家** |
| **L6** | 交付 | 完整 HTML 报告 | 最终交付物 | Claude 把关 + Codex 成稿 |

**L2 是本项目的关键筛选器**：正大杯是**市场调查**类赛事，一个再好的创意，若无法用真实、合法、可获取的数据支撑，就是死路。这一条会淘汰掉大量"听起来很美"的方向。

## 2. 团队禀赋与约束（已确认，来自 团队成员资料.txt）

**禀赋（要用足的）**
- **跨学科交叉**：3 商科 + 1 智能院。多数参赛队只有其中之一。
- **实地调研能力**：刘诗蓉有社会实践经历，擅长实地调研、团队协作与报告撰写 —— 这正是市场调查大赛的**核心得分项**。
- **财会/统计功底**：沈舒畅已过 ACCA 前五门，具备成本分析、财务测算、统计与 Python 基础数据处理能力。
- **AI 工程能力 + 算力**：spinner-bot 具备 PyTorch 能力，且有 CINECA Leonardo 超算，算力不成约束。

**约束（要避开的）**
- 团队整体工程能力以"Python 基础数据处理"为基线，**不能设计需要重型工程实现的方向**。
- 赛程有明确时间窗，需在 L0 阶段确认后倒推排期。

## 2.5 双工作流（并行推进）

Claude Code 与 Codex **同时推进**，不是串行等待。分工依据是 **「只有谁能做」** 而非「谁更快」：

| | Claude Code（把关全局） | Codex（承担体量） |
|---|---|---|
| **职责** | 框架设计、方向判断、证据定级、结论收敛、最终把关 | 全网采集、资料抄录、批量整理、格式化落盘 |
| **特点** | 消耗高但不可外包 | 体量高但可标准化 |
| **通信** | 写部署文档 → | → 读文档、执行、在回复区作答 |
| **读什么** | 只读「Codex 回复区」摘要 | 读全部原始网页与素材 |

**Claude Code 持续工作，不因等待 Codex 而中断**。等待期间推进不依赖上游产出的工作（如团队禀赋分析、报告设计规范、下一层任务书预备）。

**全局把控的责任**：确保 L0→L6 每一级的结论都是上一级的合法推论，且全链条不出现"论证很美但落地不能"的断点。

### L5 的收敛原则：输出「方向簇」而非单一选题

用户明确要求：**不要只收敛到单一选题，最好给出几个相近的选题方向**。

因此 L5 的产出设计为**一个方向簇**：

- 数个方向**共享同一个核心洞察与技术底座**，在**应用场景 / 数据来源 / 目标对象**上分化；
- 每项给出：核心命题、目标场景、所需数据、技术方案、差异化点、主要风险、团队适配度；
- 附**对比矩阵**，并由 Claude Code 给出**主推建议**（说明倾向哪个及理由）；
- 附带**切换成本评估**：若主推方向在数据获取上受阻，能否低成本切换到簇内其他方向。

**为什么这样设计**：数据可得性（L2）是最大的不确定性来源。方向簇让团队**在调研过程中保有回旋余地**，避免"赌一个方向、发现数据拿不到、全盘重来"。同时，几个相近方向也把选择权交还给团队，符合"选题应由调研提出并由团队确认"的初衷。

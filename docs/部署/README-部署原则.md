# 部署原则：主干 / 支线

**日期**：2026-10-15
**性质**：项目架构原则，由用户明确指示 + 一次失败教训固化而来

---

## 一、核心原则

> **主干任务由 Claude Code 自己做；支线任务才下发给 Codex。**

**原因**：Codex 的交付**必定有延迟**。若把关键路径上的任务交给它，整个项目会被它的响应速度卡住 —— 这是不可接受的架构缺陷。

---

## 二、主干 vs 支线的判别

| | 🔴 主干（Claude 自做） | 🟢 支线（可下发 Codex） |
|---|---|---|
| **判据** | 阻塞后续步骤的关键路径 | 不阻塞任何人的并行工作 |
| **典型** | 赛事约束分析、机会识别、方向判断、数据可行性判定、方向簇收敛、报告把关 | 通用数据源手册、竞品素材搜集、往届作品全量整理、文献批量采集、格式整理 |
| **特征** | 需要判断、需要取舍、错了要返工 | 体量高、可标准化、错了影响小、可重跑 |
| **延迟容忍** | 零容忍 | 高容忍 |

**一句话判据**：**"我现在能不能不等它就把活干下去？"** 能 → 支线；不能 → 主干。

## 三、失败教训（2026-10-15）

**事件**：`DEPLOY-001`（正大杯赛事基础事实调研）被下发给 Codex。该任务是 L0 约束识别，而 L0 是**全链条的地基** —— 后续 L1–L6 全部依赖它。属于**典型主干任务**。

**结果**：Codex 领取后**零产出**（`10-素材/001-赛事基础/` 下只有空目录），且未说明情况。L0 遂成为全项目瓶颈。

**处置**：Claude Code 接管，自行完成 L0 调研（产出见 `docs/前期调研/10-素材/001-赛事基础/answers.md`）。

**教训**：
1. **下发前必须先问"这是主干还是支线"**，而不是问"这活量大不大"。
2. 主线依赖 Codex = 把项目节奏交给一个会延迟的伙伴。
3. 判断 Codex 是否故障的依据：**该任务是否已成为全项目瓶颈**。一旦成为瓶颈，立刻接管，不要等待。

## 五、给 Codex 的下发守则（此后遵循）

1. 只下发**支线**任务。
2. 支线任务应**独立可完成**，不依赖主干产出（因为主干产出时它可能还没交付）。
3. 支线任务的产出**即便延迟也不会阻塞任何人**。
4. 每个支线任务仍须编号、落盘路径明确、交付标准清晰。
5. **定期检查 Codex 是否故障**：若主线上出现"正在等 Codex"的状态，即为红灯。
